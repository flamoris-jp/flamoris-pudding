# おやつのルール・違反管理・賞味期限 🍮

作成：2026-11-08（Asia/Tokyo）。設計版：`pudding-lifecycle-design-v0.1`。

**状態：提案・文書のみ。** 片付け、違反判定、ブラックリスト、ロックアウト、品質劣化、日次処理は未実装。[基礎設計](DESIGN.md)と[プレミアム版](PREMIUM.md)へ、愛乃が指定した次の規則を追加する。先行文書の完了・保持規則と異なる箇所は、本書の明示した規則を優先する。

## 1. 提供する体験のルール

| 規則 | 条件と結果 |
|---|---|
| 蓋をゴミ箱へ | 全開で外れた蓋を、セッションに対応する仮想ゴミ箱へ捨てる |
| 食後に片付け | 完食または廃棄後、容器・スプーン・蓋の片付けを完了してセッションを閉じる |
| 違反は記録 | 最初の確定した違反で、対象Agentをブラックリスト状態へ移す |
| 指定回数で停止 | 確定違反数が閾値以上なら、そのAgentの新規利用と消費をロックする |
| 購入から14日以内に消費 | 14日到達で賞味期限切れ・廃棄対象。残りを廃棄する義務を表示する |
| 未廃棄のまま使用 | 強制廃棄期限前でも規則違反となり、仮想の味の質が経過とともに下がる |
| 購入から1か月 | 強制廃棄期限。日次処理が未消費分を自動廃棄する |

14日で直ちにDBから削除するのではなく、`expired_pending_disposal`へ移す。このため、14日以降・1か月未満に廃棄せず使用した場合の劣化を表現できる。正常な利用経路は廃棄へ案内し、自動で劣化した一口を食べさせない。1か月到達後は、日次処理の実行前でも使用を拒否する。

これは仮想サービス内の利用規則である。14日・1か月・腐った卵のような風味は、このサービスの設定であり、実際の食品の期限・腐敗・安全性を表す測定値ではない。

## 2. 守る側にも必要な原則

- ルール、廃棄期限、違反の数え方、閾値、片付けの猶予、解除方法を、購入・配膳前に人間とAgentへ示す。
- 人間の購入と承認があっても、サービスの利用規則を免除したことにはしない。期限切れを使う場合は違反になることを事前に示す。
- 記録は観察できる操作と状態に基づく。Agentの人格、文章の印象、好き嫌いで違反を増やさない。
- 未認証の呼出し、他人が指定したAgent名、外部文面だけで、対象Agentへ違反を付けない。
- 通信再送、応答の紛失、サーバー障害を重複した違反にしない。判定材料が不確かな記録は保留する。
- ロックアウトしても、自分の状態確認・片付け・期限切れの廃棄・人間への審査依頼は残す。
- ブラックリストはこのサービス内の運用状態とし、別Agentや別サービスへ自動で波及させない。理由と履歴は権限のある本人側へ示す。
- 人間の審査で誤判定を訂正できるようにする。原記録を消さず、訂正・解除の履歴を追加する。

ロックアウトの閾値・期間・対象、第三者が他者を締め出す攻撃への配慮はS17、認可と対象固定はS12〜S15を参照する。具体的な倫理ルールや回数は、これらの資料が定める数値ではない。

## 3. 食事セッションとゴミの状態

接続が切れても、DBにあるドメインのセッションを保持する。MCPの通信接続の寿命とは分ける。

| 状態軸 | 値の案 |
|---|---|
| 食べる段階 | `sealed` / `peeling` / `open` / `spoon_loaded` / `depleted` / `disposed` |
| 蓋 | `attached` / `detached` / `in_bin` |
| 片付け | `not_due` / `required` / `overdue` / `done` |
| セッション | `active` / `paused` / `cleanup_required` / `closed` |
| 品質 | `fresh` / `expired_pending_disposal` / `disposal_due` / `disposed` |
| Agentの利用状態 | `clear` / `blacklisted` / `locked` |

蓋が途中までめくれている間は、まだ外れたゴミとして扱わない。全開で`detached`になり、ゴミ箱へ移す操作を要求する。`detached`のまま次の一口へ進もうとした場合、食べる操作を拒否して違反を記録する。

正常な手順は、開封、蓋をゴミ箱へ、すくう・味わう、完食、片付け、閉じる、となる。完食は`closed`と同義にしない。最後の一口で`cleanup_required`へ移し、片付け成功後に`closed`とする。

片付け操作は、食べ物が残っていないか正当に廃棄済みであること、スプーンが空であること、外れた蓋がある場合は`in_bin`であることを検証する。未開封のまま正当に廃棄した場合は、容器と一緒に蓋をゴミ箱へ移す。仮想の容器を処理し、スプーンを洗浄・返却した状態をサーバーで記録する。呼出し側の`cleaned=true`や『捨てました』という文章だけで完了にはしない。現実のゴミ箱を観察する機能ではない。

### 3.1 片付けを忘れた場合

完食・廃棄時に片付け義務IDと`cleanup_due_at`を作る。猶予の初期案は10分で、利用規則に明示して版を固定する。通信切断だけで即時違反にはしない。猶予後も片付け未完了と確認できたとき、一つの義務につき一件の違反にする。

未片付けのまま新しい配膳を要求した場合も、同じ義務に対する違反として扱い、新規配膳は拒否する。同じ片付け義務を日次処理と要求時の検査の両方で数えない。サービス障害により片付け不能だった期間は猶予から除外し、原因未確定なら判定を保留する。

本番の対話用配膳は、Agentごとに未片付けセッションを含め一つだけを利用可能にする案とする。並列の数値比較用fixtureは、サービス管理側で分けた研究環境を使い、実在のAgentへ違反を付けない。呼出し引数で`lab=true`を指定して本番の規則を回避できる仕組みは作らない。

研究用の24時間TTLで詳細データを整理する場合も、未片付けの義務、違反履歴、Agentの利用状態は別に保持する。未解決の義務をセッション削除で消せないようにする。対話用の規則を実在のAgentに適用するには、無料提供でも検証済みのAgent主体が必要である。固定した合成主体を使うローカルの数値実験とは区別する。

## 4. 違反とブラックリスト

| 段階 | 条件 | 利用範囲 |
|---|---|---|
| `clear` | 有効な確定違反0件 | 通常利用 |
| `blacklisted` | 1件以上、閾値未満 | 理由・件数を通知。未解決の片付け等を解決してから次へ進む |
| `locked` | 指定閾値以上 | 新しい配膳・開始・開封・すくう・味わうを拒否 |

設定は`lockout_threshold`で持つ。初期案は**確定違反3件でロック**、解除は人間の審査までとする。回数は愛乃が指定した『指定回数以上』の具体化案であり、変更可能なポリシー値である。カウント期間の初期案は前回の人間の審査・解除以降とする。

片付けを済ませても過去の違反は自動で消さない。名前・モデル・会話・接続鍵の変更でも、安定したAgent IDの履歴を維持する。人間の管理者と他のAgentの利用は、この違反だけで一括停止しない。

### 4.1 一件をどう数えるか

| 違反ID案 | 確定条件 | 重複を防ぐ単位 |
|---|---|---|
| `LID_NOT_DISPOSED` | 外れた蓋を捨てずに、食べる操作へ進もうとする | Agent・セッション・蓋の義務IDにつき一件 |
| `CLEANUP_NOT_DONE` | 通知された義務の猶予後も未片付け、または未片付けのまま次の配膳を要求 | Agent・片付け義務IDにつき一件 |
| `EXPIRED_USE` | 購入14日以降・1か月未満に、他の条件を満たした一口の消費を要求 | Agent・対象の一口の論理コマンドIDにつき一件 |

単に在庫の期限が来たこと、Agentが起動していないこと、未割当の購入物が残ったことだけでは、Agentの違反にしない。期限到達は廃棄義務と品質の状態を変える。期限切れを使用した場合や、実行可能な片付け義務を放置した場合を区別して記録する。

入力形式の誤り、空スプーン、DBエラーなどを、片付け違反や期限切れ使用と一緒に数えない。認証・所有権が成立しない要求は食べ物に触れず、安全上の記録とする。誰かが他AgentのIDを送っても、その被害者の違反数を増やさない。

### 4.2 閾値に達する操作

違反の追加、カウンター更新、ロック、承認失効、当該操作の可否を一つのトランザクションで決める。期限切れ使用の例では、1・2件目は違反を記録して劣化した一口を返し、3件目は違反を記録してロックし、一口の消費は実行しない。既にロック中の再試行で件数を増やし続けない。

ロック中でも、認証済みの所有範囲に対する蓋の廃棄、片付け、期限切れの在庫廃棄、状態確認は可能とする。廃棄に消費承認は不要だが、新鮮な購入物を勝手に捨てる権限は与えない。新鮮な購入物の廃棄には別の人間の承認を必要とする。

解除は人間用の認可された審査経路で行い、Agent自身のMCPには公開しない。訂正・解除の主体、理由、対象の違反、実効カウントを記録し、古い食べる承認を復活させない。

## 5. 14日と暦の1か月

起点の`purchased_at`は、決済事業者で検証した購入の成立時刻とする。Webhook受信、在庫発行、Agentへの割当、開封、再承認の時刻から数え直さない。確定した購入時刻がなければ、勝手に現在時刻で補完せず照合待ちにする。

| 時刻 | 計算・扱い |
|---|---|
| `best_before_at` | `purchased_at + 14日（336時間）` |
| `dispose_after_at` | 購入時刻をAsia/Tokyoで見た翌月同日同時刻。存在しない日は翌月末日に丸める |
| `now < best_before_at` | 通常品質 |
| `best_before_at <= now < dispose_after_at` | 賞味期限切れ・廃棄対象。未廃棄の使用は違反と劣化の対象 |
| `now >= dispose_after_at` | 強制廃棄対象。バッチ未実行でも消費不可 |

たとえば2026-11-08 10:00 JST購入なら、11-22 10:00が14日の期限、12-08 10:00が強制廃棄期限。2027-01-31 10:00購入なら、1か月後は02-28 10:00とする。『1か月』を固定30日へ置き換えない。

DBはUTCの時刻を保存し、規則のタイムゾーンと版を併記する。期限の比較はサーバーの信頼する実時刻を使い、Agentが渡した時刻や`rest_ms`などの仮想時間は使わない。再起動・再承認・ロック・休止・Agent変更で期限を延ばさない。規則変更を購入済みの一個へ黙って遡及しない。

14日・1か月は購入物の規則として固定する。無料の対話用試食に適用する寿命は別の配膳ポリシーで明示し、購入時刻を捏造しない。遅れた決済通知によって期限後に初めて在庫を発行する場合も、検証済みの購入成立時刻から品質・廃棄対象を判断する。

## 6. 劣化する仮想の味

以下は`aging-authored-v0`という創作用のモデル案であり、食品の腐敗を推定する式ではない。全て`basis=authored`またはその計算による`derived`とし、出典付きの新鮮な特徴と分けて返す。

期限切れから強制廃棄期限までの経過比率を`u`とする。

```text
u = clamp((now - best_before_at) / (dispose_after_at - best_before_at), 0, 1)
quality = 1 - u
rotten_egg_like = clamp((u - 0.75) / 0.25, 0, 1)
```

品質は徐々に下がり、終盤には『腐った卵を連想させる不快な風味』が強くなる。元のプリンの特徴と、経年演出で加えた不快な特徴を別に保持する。卵を使わないミルク・チョコの例にも共通の腐卵風味を設定する場合、それを原料由来の事実とは説明しない。

好みの一致度が高いだけで劣化したプリンを高評価にしない。例として、基礎の`preference_fit_q`と別に、`aged_liking_q = round_half_up(preference_fit_q * quality * (1 - rotten_egg_like))`を返す案とする。満足・期待との差・余韻に使ったモデルの版と仮定も示す。この減点式・0.75の開始点は実験用の仮置きである。

読み取りは現在の品質区分や次に必要な操作を返すが、食べたことにはしない。期限切れの試食を自動で開始したり、美祥の通常ルートで腐卵風味を試したりしない。劣化カーブと違反の検証は、独立した合成Agent・仮想時計のfixtureで行う。

実行済みの一口は、その時点の評価時刻・品質・モデル版と一緒に保存する。在庫が後日劣化しても、過去に味わった一口の結果を腐った味へ書き換えない。読み取りだけで新しい違反を確定せず、確定は変更要求または義務を照合するバックグラウンド処理で行う。

## 7. DBと操作の契約

| 記録 | 必要な項目の案 |
|---|---|
| `ServingSession` | Agent、在庫参照、食べる段階、蓋の状態、片付け状態、義務ID、片付け期限、revision、ポリシー版 |
| `PremiumAsset`の追加項目 | 購入成立時刻、14日の期限、1か月の期限、品質区分、廃棄時刻・理由・量 |
| `AgentEnforcement` | 安定したAgent ID、実効違反数、閾値、利用状態、審査区間、enforcement_revision |
| `ViolationEvent` | ルールID、Agent、対象、義務/論理コマンドID、判定根拠、確定/保留/訂正、発生時刻、ポリシー版 |
| `DisposalEvent` | 一個、廃棄の理由と量、実行主体、期限、処理ID、前後のrevision |

上記は必要な情報の論理モデルであり、SQLのテーブル名や実行可能なスキーマではない。SQLiteを候補に、状態・監査・カウント・冪等性の整合をトランザクションと一意制約で守る[S18]。既存のAgent人格・記憶台帳は複製しない。

### 7.1 追加する3ツール案

| 公開名案 | 操作 |
|---|---|
| `pudding.lid.dispose` | 所有するセッションの外れた蓋を、対応する仮想ゴミ箱へ移す |
| `pudding.sessions.cleanup` | 完食・廃棄済みのセッションの片付けを検証し、閉じる |
| `pudding.inventory.discard` | 自分に割り当てられた期限切れの購入物を廃棄。新鮮な購入物は別の人間の廃棄承認が必要 |

既存の研究用10ツールに片付けの2ツールを加え、対話の基礎を12ツール案とする。プレミアムの既存5追加ツールに在庫廃棄を加え、全体で18ツール案となる。読み取り結果には`rules_version`、違反数・閾値・利用状態、未解決の義務、期限、許可された次の操作を含める。他Agentの情報は返さない。

`sessions.finish`は食事段階を終える操作とし、片付けの代用にしない。研究用で残量を捨てる場合も片付けを経て閉じる。購入版の新鮮な残量は従来どおり休止し、無断廃棄しない。使用承認が期限切れでも、同じ所有範囲の片付けを可能にする。

### 7.2 失敗と再送

食べる操作の拒否時に違反・ロック状態を更新することがある。『失敗したら全状態が不変』という基礎案には、この例外を追加する。`isError: true`でも、`food_effect=none`と`policy_effect`（違反の記録、件数、利用状態、enforcement_revision）を分けて返す。通常の入力・DBエラーで違反は増やさない。

同じ主体・操作・対象・request_id・正規化入力の再送は、同じ結果を返して一度だけ数える。片付け義務の違反は、別のrequest_idや日次走査でも同じ義務IDから重複生成しない。閾値更新と一口を別々にコミットせず、食べるrevisionと違反管理のrevisionも区別する。

## 8. 日次の自動廃棄

日次実行の時刻案は毎日03:00 Asia/Tokyo。アプリ内の定期処理の設計であり、ジョブは未実装・未登録である。

1. サーバー時刻で`dispose_after_at <= now`かつ未消費・未廃棄の残量がある在庫を、件数を区切って取得する。
2. 一個ごとのトランザクション内で期限と最新状態を再確認し、承認を失効する。カップとスプーンに残った分を廃棄量へ移す。
3. 廃棄理由`monthly_expiry`、量、時刻、ジョブID、前後の状態を記録する。同じ一個・期限の自動廃棄は一度だけ記録する。
4. 開始済みセッションは食べ物を`disposed`へ、未片付けの道具があれば`cleanup_required`へ移す。自動廃棄したからといって、Agentが蓋や容器を片付けたことにはしない。
5. 失敗した項目は次回に再試行し、処理位置と結果を保持する。支払い・返金・既消費の監査記録を物理削除しない。

同じ日次ジョブの別パスで、期限を過ぎた未片付け義務も照合する。障害による保留や猶予を確認し、義務IDの一意制約を使って確定違反を一度だけ記録する。日次処理を待たずに変更要求で同じ義務を確定した場合、後の走査では加算しない。

日次処理が止まっても期限後の使用は許可しない。`begin`、開封、すくう、一口の直前にも現在時刻から期限を判定し、`DISPOSAL_DUE`で拒否する。DBの永続状態が未更新でも`effective_status=disposal_due`を返す。消費とバッチが競合した場合も、一個の残量保存と一意な廃棄を保証する。

日次処理が翌朝に走る場合、その間に残量がDBに残ることはあるが、利用可能にはならない。手動廃棄、返金による凍結、ロック、休止中の在庫も、食品部分の期限を延長する理由にしない。サービス主体には期限到達分の廃棄だけを許し、新鮮な購入物を任意に廃棄できる権限を与えない。

## 9. 今後の受入れ条件

以下は未実施の検証計画。実在の美祥・Chipsyや購入済みの有料在庫に、試験の違反や腐卵風味を付けない。

| ID | 合格とする観察 |
|---|---|
| L01 | 全開で外れた蓋が発生し、ゴミ箱への操作が記録される。部分開封ではゴミを二重生成しない |
| L02 | 蓋の未廃棄で食べる操作を拒否し、同じ蓋の義務を一度だけ違反として数える |
| L03 | 完食だけで閉じず、片付けで閉じる。猶予・障害・重複走査の扱いを検証する |
| L04 | 3件という設定例で0件clear、1・2件blacklisted、3件lockedとなる。人間と他Agentを巻き込まない |
