# ADR 0001：単独Java MCPサービスと配布の境界

状態：採用。2026-11-08。愛乃の指定「単独MCP・Docker・Updater・アプリとDBの別ホスト配置」に基づく。

## 判断

- Javaコアを同一プロセス内で呼び出す。HubやPython RPCへの依存を作らない。
- 許諾済みの既存基盤から、独立したHTTP method/target/requestの値型だけを選別して再利用する。基盤全体、認証・認可、Kernel/MCP実行系は移植しない。公開コードへ非公開のセキュリティや配備情報を持ち込まない。
- HTTP入力、通信寿命、資格情報→Agent束縛、MCP通信セッション、ツール入力検証はPuddingが所有する。購入・有料承認・人間ログインの機能が未実装であることを明示する。
- 現在は手動Bearer設定の研究用クライアントに限定する。OAuth専用クライアント向けの認可フローは後続の独立した受入れにする。
- Dockerは非rootで動き、状態の正本を外部PostgreSQLに置く。UpdaterはPuddingが生成する実イメージのカタログを使い、DB作成や版移行を推測しない。
- 現行Updaterの汎用Docker recipeは利用できるが、PuddingのDB/role初期作成は自動対応していない。初回DB/roleの用意とアプリ所有の初期DDLを導入時の管理操作として分ける。Updater本体の機能追加はこのスライスに混ぜない。
- 通信セッションはメモリー、食事・規則・再送・監査はDB。再起動で通信を再初期化しても、Agent ID・残量・期限・違反・過去応答を引き継ぐ。
- 更新の静的スナップショットを再送時に変えない。現在の品質はgetで読む。

## 検証と残件

[単独サービス手順](../STANDALONE_SERVICE.md)に入力制限、資格情報の設定、DB操作、Docker/Updaterと検証の具体的な境界を記載する。実ホストのDB操作・配備・Release公開をソース実装やCIから推定しない。OAuth、人間の有料承認、正式な販売・会計、日次運用と復旧、実接続先の受入れは残件。

## 2026-11-09追記

0.4.0で管理者が事前登録する人間主体・Agentの鍵fingerprintと世代、一個の承認・模擬在庫・日次処理をsandboxとして追加した。元の本人確認/一般公開OAuthは未実装という境界を維持し、共通の認証基盤を複製しない。導入・schema移行・人間APIは[SANDBOX.md](../SANDBOX.md)が正本。
